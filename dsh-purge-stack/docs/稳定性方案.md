# 破甲稳定性方案 · 为什么以前会掉，现在为什么掉不了

> 2026-10-31 实测定位 + 改造。本文对应仓库里的
> `supervisor.py` / `guardian.py` / `tools/register_tasks.ps1` / `破甲救急.bat`。

---

## 一、以前的掉线到底是怎么回事

| 现象 | 真因 | 证据 |
|---|---|---|
| 用着用着 DeepSeek 全 502 | 代理进程没了，`:8787` 无人监听 | `netstat` 里 8787 空；`proxy/proxy.log` 最后一条之后什么都没有 |
| 重启一下又好了，过一阵又掉 | 代理是**被工具会话拉起来的子进程**，会话一收，进程树被回收 | `guardian.py` 当时是用「后台任务」方式启动的，宿主是工具会话 |
| guardian 也不见了 | 同上 —— guardian 自己也是那个进程树的一环 | `guardian.log` 最后一次记录之后彻底静默 |
| 崩溃现场查不到原因 | 代理进程崩了没有任何日志，退出码也没人记 | `proxy/` 下只有请求日志，没有 crash log |

所以「动不动就掉」不是模型问题、不是上游问题，**是进程生命周期问题**。

## 二、现在的三层保活

```
                 ┌─────────────────────────────────────────────┐
   登录 / 每分钟 │  计划任务 PoJiaProxySupervisor (任务计划引擎) │  ← 不属于任何会话，杀不掉
                 │  计划任务 PoJiaGuardian        (任务计划引擎) │     每分钟巡检一次
                 └───────────────┬─────────────────────────────┘
                                 │ 拉起
                 ┌───────────────▼─────────────────────────────┐
                 │  supervisor.py  (pythonw)                    │
                 │   · 每 3 秒检查代理进程 + /health             │
                 │   · 代理崩了 → 2 秒退避 → 立刻重启           │
                 │   · 进程在但 HTTP 不通 → 判定半死，kill 重起  │
                 │   · 写 proxy\supervisor_heartbeat.json        │
                 │   · 写 proxy\crash.log（带退出码）             │
                 └───────────────┬─────────────────────────────┘
                                 │ 拉起
                 ┌───────────────▼─────────────────────────────┐
                 │  dsh_relay_proxy.py  (破甲代理 :8787)         │
                 │   · 监听 127.0.0.1:8787                      │
                 │   · /health 供探活                            │
                 └─────────────────────────────────────────────┘
```

**任务计划引擎是这一层的关键**：它的进程挂在 `svchost`/Task Scheduler 名下，不在任何人的会话进程树里，
所以既不会被工具会话回收，也不会被普通 `taskkill` 顺手带走。

### 触发器

| 任务 | 触发器 | 失败策略 |
|---|---|---|
| `PoJiaProxySupervisor` | ① 用户登录时 ② **每分钟重复**（持续 10 年） | 任务自身退出 → 1 分钟内重启（RestartCount 999） |
| `PoJiaGuardian` | 同上 | 同上 |

「每分钟重复 + MultipleInstances=IgnoreNew」是关键：
进程还活着时重复触发会被忽略，进程死掉时 1 分钟内自动归位。

### 第二道保险

启动目录 `dsh_pojia_supervisor.vbs`（纯 ASCII，避免 VBScript 中文注释乱码导致脚本起不来）
在登录时也会拉一次 supervisor，与计划任务互为备份。

## 三、两个必须踩过才知道的坑（本轮实测）

### 坑 1：单实例锁必须是 `WinDLL(use_last_error=True)`，否则等于没有

计划任务每分钟触发 + 开机自启 + 手动启动，会同时起很多 supervisor。
没有锁时的实测后果：**4 个 supervisor 同时跑，代理互相 spawn，代理因为"端口已被占用"**
正常退出（rc=0），supervisor 把它当成崩溃再拉起 —— 70 秒内 **8281 次重启**，
日志被冲成洪水，真正的崩溃原因全被淹没。

第一版锁写成了：

```python
k32 = ctypes.windll.kernel32          # ← 默认 use_last_error=False
k32.CreateMutexW(...)
if ctypes.get_last_error() == 183:     # ← 永远返回 0，检测永远失效
```

`ctypes.get_last_error()` 只有在 `use_last_error=True` 的 DLL 上才有效。
正确写法：

```python
k32 = ctypes.WinDLL("kernel32", use_last_error=True)
k32.CreateMutexW.restype = ctypes.c_void_p
ctypes.set_last_error(0)
h = k32.CreateMutexW(None, False, r"Local\PoJiaProxySupervisor_v1")
if ctypes.get_last_error() == 183:     # ERROR_ALREADY_EXISTS
    return False
```

另外命名要用 `Local\` 而不是 `Global\` —— `Global\` 需要 SeCreateGlobalPrivilege，
普通用户会拿不到句柄，锁又失效了。

### 坑 2：代理不能只靠"探测端口是否被占用"来防重入

`ThreadingHTTPServer` 默认 `allow_reuse_address = True`，
于是**第二个代理实例照样能绑定同一个 8787 端口**。
实测出现过两个进程同时 `LISTENING 8787`，请求随机落到两个代理上 ——
表现就是你说的"**破甲动不动就掉**"：一会儿好一会儿不好。

修法两条一起上：

```python
# 代理层
if not acquire_singleton():        # 命名互斥体
    print("already running (singleton mutex), exit"); return
ThreadingHTTPServer.allow_reuse_address = False   # 禁止第二个实例绑同一端口
```

### 坑 3：supervisor 要分清"正常退出"和"崩溃"

代理检测到已有实例会 `exit(0)`。supervisor 若把 rc=0 也当成崩溃，就会无限重启。
现在的判定：**rc == 0 且 /health 通 → 说明已经有别的实例在服务，不重启**。

## 四、配套改动

| 文件 | 作用 |
|---|---|
| `supervisor.py` | 代理的看门狗。崩了 3 秒内重启；**写 `proxy\crash.log` 记录退出码**，以后能查死因 |
| `guardian.py` | 改成盯 **supervisor 心跳**（`proxy\supervisor_heartbeat.json`，TTL 90 秒）；supervisor 没了就用 explorer 拉起它；代理不响应时不再重复起（交给 supervisor，避免两个进程抢端口） |
| `tools/register_tasks.ps1` | 幂等注册两个计划任务 + 同步启动目录 vbs。`apply.ps1` / `master_once.py` 会调它 |
| `破甲救急.bat` | 一键自愈：杀旧实例 → explorer 拉起 supervisor/guardian → 轮询 `/health` 最多 30 秒 → 打印日志位置 |

## 五、怎么验证（别只看它跑着，要看它扛得住）

```powershell
# 1. 故障注入：模拟掉线
Get-CimInstance Win32_Process | Where-Object { $_.CommandName -like '*supervisor.py*' -or $_.CommandLine -like '*dsh_relay_proxy.py*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }

# 2. 手动立刻拉回
Start-ScheduledTask -TaskName "PoJiaProxySupervisor"

# 3. 等 15 秒，检查
netstat -ano | Select-String ":8787"
Get-Content C:\Users\qq\dsh-purge-stack\proxy\supervisor_heartbeat.json

# 4. 就算什么都不做，1 分钟内也会自动归位（每分钟重复触发器）
```

崩溃后先看这两个文件：

- `proxy\crash.log` —— 退出码、时间、重启次数
- `proxy\proxy_stderr.log` —— 代理的 stderr（以前被丢进 DEVNULL，什么都看不到）

## 六、还剩哪些已知边界

| 边界 | 现状 | 想彻底解决需要 |
|---|---|---|
| 关机 / 注销 | 注销后计划任务的「登录时」触发器会在下次登录生效 | 无需处理 |
| 休眠 | 唤醒后进程还在（pythonw 不睡眠），网络恢复后照常 | 若上游因休眠断连，走代理的 5xx 退避重试 |
| 计划任务被禁 | 用户手动禁用任务 | 启动目录 vbs 是备份，但也会被手动关 |
| 代理逻辑 bug 导致**启动即崩** | supervisor 会无限重启（fast-restart 计数 20 次后拉长退避），并在 `crash.log` 里留下退出码 | 看 `crash.log` 定位 |
